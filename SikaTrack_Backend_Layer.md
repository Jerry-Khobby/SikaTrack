# SikaTrack — Backend Layer

**Scope:** the API and database that receive structured transaction data from the data engineering layer (and later, the mobile client), store it, and serve it to the dashboard. This doc also covers how to run your **first real end-to-end test** across the whole pipeline — phone to dashboard.

**Input contract (from Data Engineering layer):** structured, categorized, flagged transaction records (see Data Engineering Layer doc, section 1 schema + category/is_recurring fields).

---

## 1. Database Schema (Postgres via Supabase)

```sql
users (
  id, phone_number, created_at
)

transactions (
  id, user_id, provider, direction, amount,
  counterparty, transaction_type, balance_after,
  category_id, is_recurring, parse_status,
  raw_text, occurred_at, created_at
)

categories (
  id, name, is_default
)

recurring_flags (
  id, transaction_group_id, interval_days, confidence, detected_at
)
```

Seed `categories` with the list from the Data Engineering Layer doc before ingesting any real data.

---

## 2. API Endpoints (FastAPI)

| Endpoint | Purpose |
|---|---|
| `POST /transactions/ingest` | Accepts a batch of structured transactions from the data engineering pipeline (or later, the mobile client) |
| `GET /transactions` | List transactions, filterable by date range, category, direction |
| `GET /summary/monthly` | Aggregated spend by category for a given month |
| `GET /transactions/recurring` | List flagged recurring charges |
| `POST /auth/*` | Basic auth — use a library (`passlib`) or Supabase Auth directly rather than rolling your own |

### `POST /transactions/ingest` — request shape
```json
{
  "transactions": [
    {
      "provider": "mtn_momo",
      "direction": "credit",
      "amount": 50.00,
      "counterparty": "Kojo Mensah",
      "transaction_type": "transfer",
      "balance_after": 320.15,
      "category": "Transfers-Personal",
      "is_recurring": false,
      "raw_text": "...",
      "occurred_at": "2026-08-14T09:32:00"
    }
  ]
}
```

Make this endpoint **idempotent** — if the same transaction gets sent twice (retry, re-run of the pipeline), it shouldn't create a duplicate row. Use a hash of `(raw_text, occurred_at)` or similar as a uniqueness constraint.

## 3. Steps to Build

1. Set up FastAPI project, connect to Supabase Postgres connection string
2. Build schema via Alembic migrations
3. Build `POST /transactions/ingest` first — everything else depends on data existing
4. Build `GET /transactions` and `GET /summary/monthly` next
5. Add auth
6. Deploy to Render (free tier), confirm it's reachable from outside your laptop

**Done when:** you can `curl` a real parsed transaction (from your data engineering layer output) into the ingest endpoint and query it back out via `GET /transactions`.

## 4. CORS and Networking (relevant once the mobile client exists)

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],  # tighten before any public launch
    allow_methods=["*"],
    allow_headers=["*"],
)
```

Remember for later mobile testing: Android emulator reaches your laptop at `10.0.2.2`, not `localhost`; a physical device needs your laptop's LAN IP; Android blocks plain HTTP to non-localhost hosts by default.

## 5. End-to-End Real Data Test — Your First Full Pipeline Run

This is the test that actually proves the project works, not just each layer in isolation. Do this before building the mobile client or dashboard — a working pipeline with a database you can query is a legitimate milestone on its own.

1. **Collect** — export and filter your real SMS (Data Collection Guide)
2. **Parse** — run your parser against the real filtered file (Data Engineering Layer doc, Sub-Phase A). Confirm parse success rate.
3. **Categorize + flag** — run categorization and recurring detection over the parsed output. Confirm coverage rate.
4. **Ingest** — POST the final structured output to your locally running (or deployed) FastAPI `/transactions/ingest` endpoint
5. **Verify** — query `GET /transactions` and `GET /summary/monthly`, confirm the numbers match what you'd expect from manually checking a few of your real messages
6. **Spot-check** — pick 5 transactions at random from the API response, go back to the original SMS on your phone, confirm every field is correct

**This is your first real milestone worth documenting** — a screenshot of real category breakdown numbers from your own actual spending, generated by your own pipeline, is a far stronger artifact than any architecture diagram.

### What "good" looks like at this stage
- Parse success rate: aim for 90%+ on real data before moving on: lower than that means template coverage gaps worth fixing now, not later
- No duplicate transactions after re-running ingestion twice (idempotency check)
- Category coverage: doesn't need to be perfect yet — this improves over time as you add rules

### If something's wrong
- Numbers don't match your real spending → check the parser first, then categorization rules, in that order (parser errors compound downstream)
- Duplicates appear → check your idempotency key logic in the ingest endpoint
- Everything lands as `Uncategorized` → check that transaction_type is being set correctly by the parser; categorization depends on it

## 6. Handoff Forward

Once end-to-end testing passes with real data, you have two parallel next steps (can be done in either order or together): the mobile client (to automate step 1-4 instead of running scripts manually) and the dashboard (to visualize what's already in the database). Both consume the same backend API — no new contract needed.

**Done when (full layer checklist):**
- [ ] Schema created in Supabase
- [ ] `/transactions/ingest` working and idempotent
- [ ] `/transactions` and `/summary/monthly` returning correct data
- [ ] Deployed to Render, reachable externally
- [ ] Full end-to-end test run with real personal data, spot-checked against original SMS
