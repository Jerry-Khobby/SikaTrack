# Data model

One Postgres server, two schemas:

- **`app`**: owned by the backend (Alembic migrations). Users, sessions, wallets, uploads,
  provisional transactions, user corrections, budgets, notifications.
- **`dw`**: owned by the pipeline (`data-engineering/sql/migrations`). The backend has a
  read-only role on it and reads it through user-scoped views.

## Backend tables (`app`)

Primary keys are UUIDs (`gen_random_uuid()`); the API shows them with a prefix (`usr_...`).
Timestamps are `timestamptz`; money is `numeric(14,2)`, the same as the warehouse.

### Accounts

```sql
app.user (
  id               uuid PRIMARY KEY,
  phone_number     varchar(16) NOT NULL UNIQUE,   -- +233241234567
  display_name     varchar(80),
  status           varchar(12) NOT NULL DEFAULT 'active',  -- active | deleting | deleted
  delete_after     timestamptz,                   -- set by DELETE /v1/me
  settings         jsonb NOT NULL DEFAULT '{}',   -- low_balance_threshold, notify.*
  onboarding       jsonb NOT NULL DEFAULT '{}',
  pipeline_due_at  timestamptz,                   -- debounced "run the pipeline for me" (see ingestion doc)
  created_at       timestamptz NOT NULL DEFAULT now(),
  updated_at       timestamptz NOT NULL DEFAULT now()
)

app.otp_request (
  id               uuid PRIMARY KEY,
  phone_number     varchar(16) NOT NULL,
  code_hash        varchar(128) NOT NULL,         -- argon2id, never the code itself
  attempts         smallint NOT NULL DEFAULT 0,
  expires_at       timestamptz NOT NULL,
  consumed_at      timestamptz,
  requested_ip     inet,
  created_at       timestamptz NOT NULL DEFAULT now()
)  -- rows older than a day are deleted by a cleanup job

app.device (
  id               uuid PRIMARY KEY,              -- generated by the app, sent as device_id
  user_id          uuid NOT NULL REFERENCES app.user ON DELETE CASCADE,
  platform         varchar(10) NOT NULL,          -- android
  model            varchar(80),
  app_version      varchar(20),
  push_token       varchar(255),
  last_seen_at     timestamptz,
  created_at       timestamptz NOT NULL DEFAULT now()
)

app.session (
  id                   uuid PRIMARY KEY,          -- the JWT 'sid' claim
  user_id              uuid NOT NULL REFERENCES app.user ON DELETE CASCADE,
  device_id            uuid NOT NULL REFERENCES app.device ON DELETE CASCADE,
  refresh_token_hash   varchar(128) NOT NULL UNIQUE,  -- sha256 of the current token
  previous_token_hash  varchar(128),                  -- reuse of this one revokes the session
  expires_at           timestamptz NOT NULL,
  revoked_at           timestamptz,
  created_at           timestamptz NOT NULL DEFAULT now()
)
```

### Wallets (replaces `OWNER_NAMES` / `OWNER_NUMBERS`)

```sql
app.wallet (
  id               uuid PRIMARY KEY,
  user_id          uuid NOT NULL REFERENCES app.user ON DELETE CASCADE,
  provider_code    varchar(30) NOT NULL,          -- matches dw.dim_provider.provider_code
  phone_number     varchar(16) NOT NULL,
  account_name     varchar(200),                  -- as written in the SMS, upper-cased
  label            varchar(60),
  created_at       timestamptz NOT NULL DEFAULT now(),
  UNIQUE (user_id, provider_code, phone_number)
)
```

The pipeline builds each user's `Owner(names, numbers)` from these rows instead of `.env`.

### Ingestion

```sql
app.sms_batch (
  id                 uuid PRIMARY KEY,
  user_id            uuid NOT NULL REFERENCES app.user ON DELETE CASCADE,
  device_id          uuid REFERENCES app.device ON DELETE SET NULL,
  idempotency_key    uuid NOT NULL,
  request_hash       char(64) NOT NULL,           -- detects the same key with a different body
  source             varchar(16) NOT NULL,        -- initial_scan | incremental | live
  raw_object_key     varchar(500),                -- raw/users/<user_id>/sms/<date>/<batch_id>.jsonl
  received           integer NOT NULL,
  accepted           integer NOT NULL,
  duplicates         integer NOT NULL,
  latest_date_ms     bigint,
  status             varchar(12) NOT NULL DEFAULT 'received',  -- received | processing | loaded | failed
  pipeline_run_id    varchar(40),
  response           jsonb NOT NULL,              -- returned again for a repeated key
  created_at         timestamptz NOT NULL DEFAULT now(),
  loaded_at          timestamptz,
  UNIQUE (user_id, idempotency_key)
)

app.sms_seen (
  user_id          uuid NOT NULL REFERENCES app.user ON DELETE CASCADE,
  message_id       char(16) NOT NULL,             -- the pipeline's make_message_id()
  batch_id         uuid NOT NULL REFERENCES app.sms_batch ON DELETE CASCADE,
  date_ms          bigint NOT NULL,
  PRIMARY KEY (user_id, message_id)
)  -- the duplicate check on upload; no SMS text here

app.provisional_transaction (
  user_id          uuid NOT NULL REFERENCES app.user ON DELETE CASCADE,
  message_id       char(16) NOT NULL,
  transaction_nk   varchar(80) NOT NULL,          -- same formula as the pipeline: provider:txn_id or provider:msg:<message_id>
  batch_id         uuid NOT NULL REFERENCES app.sms_batch ON DELETE CASCADE,
  occurred_at      timestamptz NOT NULL,
  provider_code    varchar(30),
  template         varchar(50),
  transaction_type varchar(30),
  direction        varchar(6),
  amount           numeric(14,2),
  fee              numeric(14,2),
  tax              numeric(14,2),
  balance_after    numeric(14,2),
  counterparty     varchar(200),
  reference        varchar(255),
  category_name    varchar(50),
  category_rule    varchar(80),
  parse_status     varchar(10) NOT NULL,          -- parsed | unparsed | ignored
  PRIMARY KEY (user_id, message_id)
)  -- deleted when its batch is loaded by the pipeline
```

### User input

```sql
app.category_override (
  user_id          uuid NOT NULL REFERENCES app.user ON DELETE CASCADE,
  transaction_nk   varchar(80) NOT NULL,          -- stable across runs, same for provisional and final
  category_name    varchar(50) NOT NULL,          -- must exist in dw.dim_category
  note             varchar(500),
  updated_at       timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, transaction_nk)
)

app.counterparty_preference (
  user_id            uuid NOT NULL REFERENCES app.user ON DELETE CASCADE,
  counterparty_name  varchar(200) NOT NULL,       -- normalised name, as in dw.dim_counterparty
  alias              varchar(80),
  default_category   varchar(50),
  updated_at         timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, counterparty_name)
)

app.recurring_preference (
  user_id          uuid NOT NULL REFERENCES app.user ON DELETE CASCADE,
  recurring_series char(12) NOT NULL,             -- dw.fact_transaction.recurring_series
  user_state       varchar(16),                   -- expected | cancel_planned | not_recurring
  label            varchar(80),
  updated_at       timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, recurring_series)
)

app.budget (
  id                uuid PRIMARY KEY,
  user_id           uuid NOT NULL REFERENCES app.user ON DELETE CASCADE,
  category_name     varchar(50) NOT NULL,
  monthly_limit     numeric(14,2) NOT NULL CHECK (monthly_limit > 0),
  alert_thresholds  numeric(4,3)[] NOT NULL DEFAULT '{0.8,1.0}',
  created_at        timestamptz NOT NULL DEFAULT now(),
  updated_at        timestamptz NOT NULL DEFAULT now(),
  UNIQUE (user_id, category_name)
)
```

Notes are kept with the override row, so a note alone is an override with the rule's category.
The pipeline applies these when categorising: precedence is **transaction override >
counterparty default > rules**, and the result's `category_rule` records which one
(`user:override`, `user:counterparty`, or the rule as today).

### Notifications

```sql
app.notification (
  id               uuid PRIMARY KEY,
  user_id          uuid NOT NULL REFERENCES app.user ON DELETE CASCADE,
  kind             varchar(30) NOT NULL,
  title            varchar(120) NOT NULL,
  body             varchar(500) NOT NULL,
  link             varchar(200),
  dedupe_key       varchar(120) NOT NULL,         -- e.g. budget:food:2026-10:0.8
  pushed_at        timestamptz,
  read_at          timestamptz,
  created_at       timestamptz NOT NULL DEFAULT now(),
  UNIQUE (user_id, dedupe_key)
)
```

`dedupe_key` is what makes "at most one alert per threshold per month" a database guarantee
instead of a hope.

### Audit

```sql
app.audit_event (
  id         bigserial PRIMARY KEY,
  user_id    uuid,                                -- kept after deletion as an opaque ID
  action     varchar(40) NOT NULL,                -- sign_in, wallet_added, account_deleted, ...
  detail     jsonb NOT NULL DEFAULT '{}',         -- IDs and counts only, never SMS text
  created_at timestamptz NOT NULL DEFAULT now()
)
```

## Warehouse changes (`dw`)

The warehouse is single-user today. Migration **`004_users`** in
`data-engineering/sql/migrations/` makes it multi-user. This is phase 0 and the biggest change
the backend forces on the data layer.

| Table | Change | Why |
|---|---|---|
| `dw.dim_user` | **New**: `user_key serial`, `user_id uuid UNIQUE` (= `app.user.id`), `created_at` | Conformed user dimension; no personal data, the phone number stays in `app` |
| `dw.fact_transaction` | Add `user_key` (FK, `NOT NULL`, index `(user_key, occurred_at)`). The natural key becomes unique **per user**: `UNIQUE (user_key, transaction_nk)` | Two users can receive the same provider transaction (sender and receiver both get an SMS for one transfer) |
| `dw.dim_counterparty` | Add `user_key`; unique on `(user_key, counterparty_name)` instead of the name alone | Who "KOFI MENSAH" is depends on whose phone it's on; counterparties are personal data |
| `dw.etl_run` | Add `user_key` (nullable for old runs) | Runs, quality reports and monitoring become per user |
| `dw.dim_date`, `dim_time`, `dim_provider`, `dim_transaction_type`, `dim_category` | Unchanged, shared | Not personal |
| `dw.v_fact_transaction` | Add `user_id`; Power BI filters on your user | Your dashboard keeps working |

Backfill: create your user, set `user_key` on every existing row to yours, then add the
`NOT NULL` and the new unique constraints, all in the one migration transaction.

### Pipeline changes that go with it

| Today | Per user |
|---|---|
| Raw zone `raw/sms/<date>/<file>.xml` | Also `raw/users/<user_id>/sms/<date>/<batch_id>.jsonl` (app uploads). XML backups you import go under your user too |
| One run processes every backup | The DAG maps over users with new data (Airflow dynamic task mapping), one isolated run per user |
| `Owner.from_env()` | `Owner` from the user's `app.wallet` rows |
| Recurring detection, balance checks, quality gates over everything | The same, per user |
| Category rules only | Rules, then the user's counterparty defaults and overrides (read from `app`) |
| Load upserts on `transaction_nk` | Upserts on `(user_key, transaction_nk)`; deletes a user's rows when they delete their account |
| Emails the operator on failure | Same, plus `POST /internal/pipeline-events` to the backend for every run |

The JSONL raw format holds the same three fields the XML does (`sender`, `date_ms`, `body`), so
`filter_sms.make_message_id` gives the same ID for an SMS whether it came from a backup or the
app. Your old backups and new uploads deduplicate against each other automatically.

## How the backend reads `dw`

A read-only Postgres role `sikatrack_api_ro` with `USAGE` on `dw` and `SELECT` on views only.
Every view takes the user from the session, so a forgotten `WHERE` can't leak another user's
rows:

```sql
-- set by the backend on each connection checkout:
SET LOCAL app.user_id = '<uuid>';

CREATE VIEW dw.api_transaction AS
SELECT f.*, c.counterparty_name, c.counterparty_kind, cat.category_name, cat.category_group
FROM dw.fact_transaction f
JOIN dw.dim_user u USING (user_key)
JOIN dw.dim_counterparty c USING (counterparty_key)
JOIN dw.dim_category cat USING (category_key)
WHERE u.user_id = current_setting('app.user_id')::uuid;
```

The backend's session dependency sets `app.user_id` from the access token before any query
runs. Row-level security (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY` with the same condition)
can be added on the base tables in phase 7 as a second layer.

## ID mapping (API ↔ database)

| API | Database |
|---|---|
| `usr_<uuid>` | `app.user.id` = `dw.dim_user.user_id` |
| `txn_<base64url>` | Final: encoded `transaction_nk`. Provisional: the same, because provisional rows use the same formula, so an ID doesn't change when the pipeline confirms the transaction |
| `cpt_<base64url>` | Encoded normalised `counterparty_name` (unique per user) |
| `rec_<series>` | `recurring_series` (12 hex characters, already a hash) |
| `bat_<uuid>`, `wal_<uuid>`, `bud_<uuid>`, `ntf_<uuid>` | `app` primary keys |

IDs are encoded, not encrypted: the backend always checks they belong to the caller, and an ID
from another user returns `404`.
